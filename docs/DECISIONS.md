# Architectural Decisions

# ADR-001: Выбор языка программирования
Date: 2026-08-11
Status: Accepted
Context: Для написания Telegram бота требуется язык с развитой экосистемой библиотек для AI и ML, а также хорошей асинхронной поддержкой.
Decision: Выбран Python (версия 3.13+).
Alternatives: Node.js, Go.
Reason: Python является стандартом de facto в сфере AI и интеграции с LLM. Aiogram является одной из лучших асинхронных библиотек для Telegram на текущий момент.
Consequences: Потребуется строгий контроль зависимостей (через requirements.txt/pyproject.toml) и изолированные виртуальные окружения.

# ADR-002: PostgreSQL как основная БД с pgvector
Date: 2026-08-11
Status: Accepted
Context: Проекту необходимо хранить как реляционные данные (пользователи, сообщения), так и векторные эмбеддинги для семантического поиска.
Decision: PostgreSQL с расширением pgvector.
Alternatives: Использование отдельной векторной базы данных (Qdrant, Milvus, Pinecone).
Reason: Снижение операционной сложности (одна СУБД вместо двух), транзакционная целостность при записи фактов и их эмбеддингов, поддержка гибридного поиска средствами одной СУБД.
Consequences: Зависимость от специфичного расширения PostgreSQL; в случае экстремально высоких нагрузок на векторный поиск может потребоваться миграция.

# ADR-003: Redis для кэша и очередей
Date: 2026-08-11
Status: Accepted
Context: Необходимо управлять асинхронными фоновыми задачами, кэшировать данные и ограничивать частоту запросов.
Decision: Использовать Redis.
Alternatives: RabbitMQ, Celery с базой данных в качестве брокера.
Reason: Легковесность, высокая производительность, подходит как для очередей (RQ или Celery-Redis), так и для кэширования/блокировок.
Consequences: Redis не является долговременным хранилищем. Важные данные должны периодически синхронизироваться в PostgreSQL.

# ADR-004: Изоляция абстракции LLM и использование google-genai SDK
Date: 2026-08-11
Status: Accepted
Context: На текущий момент используется Google Gemini, но LLM модели быстро развиваются.
Decision: Использовать актуальный официальный `google-genai` SDK и создать абстрактный интерфейс `LLMProvider` для всех вызовов моделей.
Alternatives: Прямое использование SDK `google-genai` в бизнес-логике или использование устаревшего `google-generativeai`.
Reason: Защита от vendor lock-in; легкость тестирования (можно создать MockProvider); использование актуального SDK.
Consequences: Некоторое усложнение архитектуры.

# ADR-005: Многоуровневая архитектура памяти и неразрушающая история
Date: 2026-08-11
Status: Accepted
Context: Бот должен обрабатывать большие объемы истории переписки, которую невозможно полностью передать в контекст LLM.
Decision: Сохранять всю историю в сыром виде. Параллельно (асинхронно) извлекать из нее факты, темы и саммари (многоуровневая память). LLM получает только релевантный контекст.
Alternatives: Постоянная суммаризация всего контекста, отбрасывание старых сообщений.
Reason: Сохранение исходного контекста позволит в будущем переобучать модели или перестраивать структуру памяти, отвечать с прямыми ссылками на исходные сообщения.
Consequences: Требуется значительный объем дискового пространства в БД; сложные алгоритмы гибридного поиска.
